## On colour

Neither the brief nor the lecture slides say anything about colour, so it carries no
marks on its own. What does matter is that the figures look like one set: the Week 5
slides ask for one font throughout and a caption on every figure, and a report whose
diagrams are styled differently from each other reads as careless.

All four therefore use the same blue. This was not the first choice. Three of them
were drawn in plain black and white first, which is the more conventional look for
UML, but the sequence diagram is generated by a tool that always draws its frames in
blue and cannot be forced to match. Making the other three blue was the only way to
get one consistent set, so that is what was done. The black and white versions are
kept in `bw/` in case the sequence diagram is ever redrawn by hand.

Colour is used to mean something rather than to decorate:

- Solid blue: classes and use cases that this project wrote.
- Dashed grey: things outside the project. `JFrame` in Figure 4 is part of Swing, and
  "Place the fleet at random" in Figure 1 is a use case the player never performs.
- Dark blue fill: the actor, so it reads as different in kind from a use case.

Nothing depends on colour alone. Every figure still reads correctly printed in black
and white, because the dashed outlines and the arrowheads carry the same information.

## Figure numbers

The file names still use the letters A to D, which is how the diagrams were drawn,
but the report numbers every figure in one sequence so that Word can build a table of
figures: the four diagrams are Figures 1 to 4 and the ten screenshots are Figures 5
to 14. The table above gives the mapping.

## Figure 4 was redrawn

Figure 4 was redrawn on 19 November, after the difficulty setting and the fleet panel
were added. The model it showed had ten classes; the code now has fourteen, so the
earlier version no longer described the submitted code. The document it was drawn in
is a new one, listed in the table above; the superseded one was
`16ced3e3-aa11-4f73-b39d-c82c6ce21f1d`.

The four classes added to the figure are `Difficulty`, `ShipStatus`, `BoardPanel` and
`FleetPanel`, together with the interface `ShotListener` that `BoardPanel` declares.
`ShotListener` is drawn as a separate box although it is a nested interface, because
the relationship it carries, a panel reporting a click to whoever built it, is the
reason the interface exists.

Figures 1, 2 and 3 were deliberately left alone. They show the design as it was
planned, which is what the planning section requires.
