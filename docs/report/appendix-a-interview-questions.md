## Where this project can supply a genuine example

Several of these questions can be answered with something the student actually built,
which is far more convincing in an interview than a textbook definition. These are
pointers to the evidence, not answers.

| Question | Something in this project to draw on |
| --- | --- |
| 1 | All four principles appear in the code; section 4.2 of the report lists where. |
| 2 | Swing handles many different components and listeners through their declared types without knowing what this project put behind them. |
| 3 | Nothing in this project uses `protected`; the honest answer is about when it *would* be right, and why this design never needed it. |
| 4 | `Board` hides the ship positions so the interface cannot leak them; `Ship` copies its cells so outside code cannot move a placed ship; the rules can be tested without a window. |
| 5 | This project uses an interface (`ActionListener`) and deliberately uses no abstract class; section 7.4 explains why. |
| 6 | `Board` has two constructors, and `RandomShipPlacer.createBoard` exists with and without a size argument. |
| 7 | Section 6 of the report: the unit checks confirmed a colour was blue, but only functional testing found that the character on the cell was unreadable. |
| 8 | Not used in this project. Lecture material, Week 7. |
| 9 | Not used in this project; there is no database. Lecture material, Week 8. |
| 10 | Every click in this game: the button raises an event and the window reacts, rather than the program asking repeatedly whether a click has happened. |
